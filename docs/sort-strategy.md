# Стратегия мониторинга: сортировка + ранний выход

## Зафиксированный алгоритм

**Решение клиента: per-page=10** (минимум для снижения нагрузки на медленный сервер).

1. GET `/cabinet/free-lot?region=N&per-page=10&sort=-DATE_CREATE`
2. Идём сверху вниз по строкам:
   - Если `id` лота **уже есть в `state.db`** → СТОП. Дальше всё старее.
   - Если `id` **нет в БД** → новый лот, добавляем в список к уведомлениям.
3. Если **все 10 строк** оказались новыми → загружаем **следующую страницу**, повторяем.
4. После завершения цикла:
   - Сохраняем новые лоты в `state.db`.
   - Шлём уведомления в Telegram.

### Обоснование per-page=10
Замеры показали: время генерации страницы линейно зависит от размера:
- per-page=20 → 81 с
- per-page=50 → 151 с
- per-page=10 → ожидаемо 50-70 с в режиме техработ, секунды в норме

Меньшая страница → меньше работы для сервера → быстрее ответ.

### Когда понадобится page=2
Только если за интервал мониторинга создано **11+ новых лотов**. На сегодня в region=1 создаётся 2-3 лота в день — то есть практически никогда.

### Потенциальная оптимизация для v2 (после MVP)
Сайт поддерживает **PJAX** (заголовок `X-Pjax: true`) — возвращает только таблицу без обёртки. Теоретически ~50 КБ вместо 268 КБ + быстрее на сервере. Не успели протестировать (сервер в техработах). Проверить в нормальный день и подключить, если работает.

## Открытие
Сайт поддерживает сортировку. Параметр `sort=-DATE_CREATE` ставит **новые лоты сверху**. Также: внутренний `data-key` (id лота) выдаётся монотонно возрастающим — **больший id = более свежий лот**.

## Доступные поля сортировки (с самого сайта)
| Поле | Назначение |
|---|---|
| `CADASTR_NUM` | кадастровый номер |
| `AREA_EGRN` | площадь |
| `numberOfCitizensLotOffered` | кол-во граждан, кому предложен |
| `responseUo` | ответственный УО |
| **`DATE_CREATE`** | **дата создания — то, что нам нужно** |
| `CREATE_ROLE_OGV_NAME` | УО, разместивший сведения |
| `DATE_UPDATE` | дата обновления |
| `freeLotStatus` | статус |

Yii2-конвенция: `sort=FIELD` = ASC, `sort=-FIELD` = DESC.

## Проверка (12.05.2026)
URL: `/cabinet/free-lot?region=1&per-page=50&sort=-DATE_CREATE`

Результат — топ 3:

Сортировка работает, id монотонные, новейшие сверху.

## Алгоритм цикла мониторинга

```python
def monitor_cycle(region: int):
    last_known_id = state_db.get_last_id(region)  # например, 9985
    page = 1
    new_lots = []

    while True:
        response = fetch(f"/cabinet/free-lot?region={region}&per-page=10"
                         f"&sort=-DATE_CREATE&page={page}")
        rows = parse_rows(response)
        if not rows:
            break

        for lot in rows:
            if lot.id <= last_known_id:
                # упёрлись в известный — дальше всё старше
                return new_lots
            new_lots.append(lot)

        # все 10 на странице — новые. Долго не работали? Идём дальше
        page += 1

    return new_lots
```

> **Замечание**: `per-page=10` — финальное решение, см. [[decisions-log]].

После цикла:
1. Сохранить все `new_lots` в state.db.
2. Обновить `last_known_id` = max(id новых).
3. Отправить уведомления в Telegram.

**Идемпотентность**: `last_known_id` обновляется ПОСЛЕ успешного сохранения всех новых. Краш до этого момента — следующий запуск переотправит те же лоты, но это лучше, чем потерять.

## Преимущества vs наивный подход (фул-скан всех страниц)

| Метрика | Фул-скан | Sort + early exit |
|---|---:|---:|
| Запросов на цикл (типично) | ~45 (для region=1 при per-page=10) | **1** |
| Запросов при пустом цикле (0 новых) | ~45 | **1** (увидели знакомый id уже в 1-й строке) |
| Запросов при «забивке» (10+ новых) | ~45 | до ~45 (как фул-скан) |
| Время цикла в норму (5с/запрос) | ~225 с | **5 с** |
| Время цикла в техработы (60с/запрос для per-page=10) | ~45 мин | **1 мин** |
| Нагрузка на гос-сервер | в десятки раз больше | минимальная |

> **Замечание**: расчёты приведены для `per-page=10` (финальное решение, см. [[decisions-log]]).

## Edge cases

### 1. Лот изменился, но id тот же
Сортировка по DATE_CREATE не реагирует на обновления. Если нужно ловить изменения статуса (`Свободен` → `Забронирован`) — нужна вторая стратегия: периодически (раз в день?) делать фул-скан с сортировкой `-DATE_UPDATE`. Но клиент сказал — нас интересуют только новые, см. [[decisions-log]].

### 2. Лот удалён из реестра / сменил статус

**Обновление 12.05.2026.** Detection пропавших лотов теперь IN-SCOPE.
Реализован через отдельный background task `full_scan` (раз в сутки) —
см. [[monitoring-plan]] → раздел «full_scan» и [[decisions-log]] → «Removal-detection».
Без уведомлений: только серая карточка в ленте.

### 3. Первый запуск (`last_known_id = 0`)
Запросов будет столько, сколько страниц. Один раз — терпимо. Сохраняем все, дальше — `last_known_id` уже актуален.

### 4. Лимит 50 не сработал, сайт начал возвращать меньше
Если на странице 10 строк, а ждали 50 — это последняя страница (стандартное поведение). Цикл выйдет естественно.

### 5. Сайт сменил названия полей сортировки
Например, переименует `DATE_CREATE` → `created_at`. Запрос вернёт несортированный список → мы можем пропустить новые лоты или зациклиться.
**Защита**: в коде валидация. Если `id[0] < id[5]` (порядок нарушен) → CRITICAL alert «парсер сломан, сортировка не работает», без обновления БД.

## Влияние на интервал между циклами

| Режим сервера | 1 запрос | Интервал между циклами | Задержка уведомления |
|---|---:|---:|---:|
| Норма (после техработ) | 5-30 с | **5 минут** | до 5 минут |
| Под нагрузкой | 30-60 с | 10 минут | до 10 минут |
| Техработы (как 12.05.2026) | 150+ с | 30 минут | до 30 минут |

Адаптивный интервал: после каждого цикла измерять время, если медленнее — увеличить.

## Почему НЕ экспорт

Сайт умеет экспортировать весь реестр (`POST /cabinet/start-export-freelot`), но это **тяжёлая асинхронная задача**:
1. POST с параметрами фильтра + списком колонок
2. Сервер ставит в очередь, отвечает «Формирование запущено»
3. Браузер опрашивает «готово?» каждые N секунд
4. Когда файл готов — скачивание XLS

**Минусы для мониторинга:**
- 3-5 запросов на цикл вместо 1
- Время — минуты вместо секунд
- На сервере **запускает тяжёлую фоновую задачу** на каждый цикл
- Заметнее в логах сайта (статус задач, очередь экспортов)
- Парсить XLS сложнее, чем HTML

**Когда экспорт уместен:**
- Разовая выгрузка для аналитики/отчёта
- Бэкап раз в неделю (исторические данные)

Добавить как отдельную фичу «Экспортировать всё в Excel» по клику клиента, не для мониторинга.
