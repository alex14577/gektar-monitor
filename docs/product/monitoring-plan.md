## Защита от смены ID-схемы

Допущение «id монотонно растёт» проверено только на наблюдениях 12.05.2026.
Если сайт когда-то сменит генерацию (рандомизация, сегментация по регионам,
переход на UUID) — наш early-exit пропустит **все новые лоты молча**.

### Алгоритм проверки между циклами

После парсинга страницы 1 в `monitor_cycle` сравниваем `max(id_new_page)`
с сохранённым `last_known_id` региона:

| Условие | Интерпретация | Действие |
|---|---|---|
| `max(id_new_page) >= last_known_id` | норма, монотонность сохранена | early-exit работает как обычно |
| `max(id_new_page) <  last_known_id` | возможна смена ID-схемы | см. ниже |

### Реакция на anomaly

1. `cycles.error = "id_schema_anomaly"`, `cycles.id_schema_check = "anomaly"`.
2. Уведомление пользователю: «Возможно, сайт изменил формат id —
   проверьте вручную».
3. **Не обновляем `last_known_id`** до подтверждения пользователем.
4. В UI кнопка «Подтвердить новую схему / Заново заиндексировать».
5. До подтверждения цикл продолжает работу, но в каждом цикле
   логирует `id_schema_anomaly` (для grep по `cycles`).
6. После подтверждения: `cycles.id_schema_check = "confirmed"`, `last_known_id`
   переинициализируется из текущей страницы 1.

### Sentinel-поле

В таблице `cycles` (см. [[data-model]] и [[db/schema|db/schema.sql]]) поле
`id_schema_check`: `ok | anomaly | confirmed`. Это единственный канал, по
которому UI/runbook отличают «всё ок» от «нужно действие оператора».

См. также: [[architecture]] §1/§7, [[ops/runbook]] (раздел «Аномалии»).
