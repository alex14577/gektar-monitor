# ADR-061 — Screen-reader / assistive-technology support is out of scope

**Status:** Accepted (2026-05-29)

## Context

В кодовой базе накопился заметный объём поддержки скринридеров (assistive
technology, AT): выделенные скрытые live-регионы `#__live_polite` /
`#__live_assert` (`base.html.jinja`), JS-анонсер `window.Monitor.announce()`
(используется в `auth.js`), `aria-live` / `aria-atomic` / `aria-relevant` на
`#feed` и баннерах, `aria-hidden` на декоре, `aria-label` на иконочных кнопках,
ARIA-роли/состояния (`role="status"`, `aria-pressed`, и т.д.).

**Этого никто не требовал.** Поддержка AT не значится в требованиях продукта, нет
WCAG-комплаенса, госконтракта или известных пользователей со скринридером.
Разметка вошла как **дефолтное поведение writer-агентов** (LLM-модели и скилл
`frontend-design` рефлекторно пишут ARIA как часть «production-grade» фронтенда),
а затем закрепилась в канон-доках (`notifications.md`, `decisions-log.md`,
`browser-feedback-mcp.md`) с WCAG-цитатами — из-за правила «docs = single source
of truth» каждый следующий агент честно ей следовал. Незапрошенное требование
само себя институционализировало.

Триггер этого ADR — баг [[../glossary|aria-live]] спама скринридера при backfill
(`gektar_monitor-9z6n`, закрыт `wontfix`): обнаружилось, что мы продолжаем тратить
ресурс на AT-корректность, которую никто не заказывал.

## Decision

**Поддержка assistive technology (скринридеры / незрячие) — ВНЕ scope проекта.**

- **Целевой пользователь** — зрячий оператор desktop-инструмента мониторинга
  торгов. Это ниша без обязательств по WCAG 2.x AT-критериям (1.3.x семантика для
  AT, 4.1.x name/role/value, live-region анонсы).
- **Существующая ARIA-разметка — grandfathered**: не удаляем (она безвредна и
  удаление = лишний риск), но и **не поддерживаем активно**. Баги уровня «AT
  ведёт себя некорректно» закрываются `wontfix`, если не появилось явного
  требования.
- **Новых AT-вложений не делать без явного запроса пользователя.** Writer- и
  review-агенты НЕ обязаны добавлять/чинить `aria-live`-анонсы, sr-only-регионы,
  AT-специфичные роли. Упоминания WCAG в канон-доках — **описание того, что код
  делает, а не binding-требование**.

### Что ОСТАЁТСЯ в scope (это НЕ AT-поддержка, а обычный хороший визуальный дизайн)

- **Контраст ≥ 4.5:1** (WCAG AA по цвету) — читаемость для всех зрячих.
- **Non-color indicators** (WCAG 1.4.1) — не полагаться только на цвет
  (помогает дальтоникам, дёшево).
- **`:focus-visible`** — видимый фокус для клавиатурной навигации.
- **`prefers-reduced-motion`** — отключение анимаций (вестибулярная чувствительность).
- **Семантический HTML** — заодно поддерживаемость и тестируемость.
- **ARIA-tree как QA-оракул** в Playwright/chrome-devtools
  (`browser-feedback-mcp.md`) — это инструмент тестирования, а не фича для
  пользователей; остаётся.

## Alternatives considered

1. **Полностью вырвать всю ARIA-разметку.** Отвергнуто: разметка уже написана,
   удаление = широкий diff + риск регрессий ради нулевой выгоды. Сунк-кост дешевле
   оставить.
2. **Оставить как есть, ничего не фиксировать.** Отвергнуто: тогда агенты,
   опираясь на WCAG-цитаты в канон-доках, продолжат тащить AT-работу по дефолту.
   Нужен явный «стоп» в каноне.
3. **Принять полноценный WCAG-комплаенс.** Отвергнуто: нет требования, нишевый
   sighted-only продукт, не оправдано по затратам.

## Consequences

- `gektar_monitor-9z6n` и любые будущие AT-only баги → `wontfix` по умолчанию.
- Канон-доки с WCAG-цитатами аннотированы ссылкой на этот ADR, чтобы не читаться
  как требование (`notifications.md`, `browser-feedback-mcp.md`).
- Если позже появится реальное требование (госконтракт / пользователь с AT) — этот
  ADR пересматривается (Superseded), и заводится отдельная a11y-инициатива.
- Визуальная доступность (контраст, фокус, reduced-motion) продолжает применяться
  как норма дизайна — она не зависит от этого решения.
