# Локальный каталог лотов

> ⚠️ **Не в MVP — отложено в v2** ([[decisions-log]]).
> В MVP уведомления о новых лотах и базовая страница «новые». Схема БД и API заложены так, что каталог добавляется без переписывания.

> Идея: у нас в SQLite уже хранятся все обнаруженные лоты. Раз они есть — построим **быстрый красивый каталог в браузере** с фильтрами, поиском и картой. Это и есть «копия сайта», только локальная, моментально откликающаяся.

## Что даёт клиенту

- **Скорость** — фильтрация по 5000 лотам в SQLite = миллисекунды, не 150 секунд как на сайте
- **Лучше UX** — современная таблица с сортировкой по любой колонке, мульти-фильтры, поиск по тексту
- **Карта** — все лоты сразу нанесены, видно где скопления, фильтры карты живые
- **Работает офлайн** — после первой синхронизации
- **Без риска** — никаких запросов к гос-серверу при работе с каталогом

## Что собираем по каждому лоту

См. [[cabinet-free-lot]] — канон полей (16 из списка + 7 из детальной карточки = 23 поля).

### Расчётные поля (вычисляются у нас)
- **Десятичные координаты** из ДМС
- **Ссылка на ПКК Росреестра**: `https://pkk.rosreestr.ru/#/search/56.0,90.0/16?text={кадастр}&type=1`
- **Ссылка на Яндекс.Карты**: `https://yandex.ru/maps/?ll={lon},{lat}&z=16&pt={lon},{lat}`
- **Ссылка на OpenStreetMap**: `https://www.openstreetmap.org/?mlat={lat}&mlon={lon}&zoom=16`
- **Площадь в гектарах**: округление до 2 знаков для UX
- **Сколько дней «свежий»**: `now - date_create`
- **Расстояние до областного центра** (опционально, при наличии справочника)

### Вид «Только новые» (главная страница)
По умолчанию открывается этот вид — лоты, появившиеся после последнего просмотра клиентом + те, которые он ещё не отметил «просмотрено». Это и есть «уведомления» в браузере, но в форме списка карточек, не toast'ов.

## Эндпоинты бэкенда

```
GET  /                       → главная (новые лоты)
GET  /catalog                → каталог-таблица
GET  /catalog/map            → каталог-карта
GET  /catalog/lot/{id}       → детальная карточка лота (из БД, не с сайта)

GET  /api/lots               → JSON-список с фильтрами и пагинацией
  ?region=87&min_area=1000&max_area=10000&status=Свободен
  &category=сельхоз&page=1&per_page=50&sort=-date_create
GET  /api/lots/map           → GeoJSON для карты (bbox-фильтр)
  ?bbox=lat1,lon1,lat2,lon2&...
GET  /api/lots/{id}          → одна карточка
POST /api/lots/{id}/mark-seen → пометить как просмотренное

GET  /api/filters/options    → доступные значения фильтров (регионы, ВРИ, ОГВ)
  → используется для заполнения дропдаунов в UI

POST /api/sync/refetch-details → принудительно перепарсить детальные карточки
  для лотов без координат (back-fill)
```

## Стратегия наполнения деталей

При первом обнаружении лота — парсим список (быстро). Детальную карточку — **в отдельном фоновом таске**, не блокируя цикл мониторинга:

```
[Цикл мониторинга]
   1. GET список → парсим 10 строк
   2. Сохраняем в БД ТОЛЬКО поля из списка
   3. Уведомляем пользователя «новый лот!»
   4. Кладём id в очередь enrichment_queue

[Фоновый enrichment-worker]
   1. Берёт лот из очереди
   2. GET /cabinet/free-lot-view?id=N (5 сек)
   3. Парсит координаты, границы, ЕГРН
   4. UPDATE lots SET lat=..., lon=..., ...
   5. Спит 5 секунд (не спамим сервер)
   6. Берёт следующий из очереди
```

Так клиент видит уведомление **сразу** (по данным из списка), а карта/детали наполняются в фоне, не мешая основному циклу.

## Back-fill для уже накопленных лотов (первый запуск)

При первом запуске у клиента БД пустая → запускаем стартовую инициализацию.

### Измеренная производительность детальных карточек (12.05.2026)
```
10 запросов /cabinet/free-lot-view?id=N параллельно
  → wall-time: 7.5 секунд (все 10 за это время)
  → каждый запрос: 6.3 — 7.5 секунд
  → размер ответа: стабильно 32.6 КБ
  → HTTP 200 на всех 10
  → ускорение vs последовательный: 9.3×
```

Сервер карточек **отлично выдерживает параллельную нагрузку** (в отличие от списка, который тяжёлый — см. [[server-performance]]). Карточка — это лёгкий SELECT по ID без сложных фильтров.

### Алгоритм back-fill

```
ШАГ 1: Сборка списков (последовательно)
  # ⚠️ MVP цикл — per-page=10 (см. [[decisions-log]]).
  # Back-fill алгоритм v2 ниже — отдельная задача каталога (v2),
  # может использовать другой per-page после согласования.
  for region in [1, 2]:
    page = 1
    while True:
      GET /cabinet/free-lot?region={region}&per-page=50&sort=-DATE_CREATE&page={page}
      сохраняем все строки в БД с базовыми полями
      if нет следующей страницы: break
      page += 1
      sleep(2s)  # вежливо
  
  Ожидание: ~5000 лотов / 50 на странице = 100 запросов
            при норм. сервере 5-10с/запрос = 8-15 минут

ШАГ 2: Enrichment деталями (параллельно по 10)
  Берём все лоты без координат, делим на батчи по 10.
  ThreadPoolExecutor(max_workers=10).
  
  Ожидание: 5000 лотов / 10 = 500 батчей × 7.5с = ~60 минут
```

**Итого первый запуск**: ~1.5 часа в фоне, после чего БД полностью заполнена со всеми координатами. UI каталога работает с первой минуты — таблица доступна, карта дозаполняется в реальном времени.

### Параметры enrichment-worker'а

```python
ENRICHMENT_PARALLELISM = 10   # одновременных запросов карточек
ENRICHMENT_RATE_DELAY = 0.5   # секунд между батчами (вежливость)
ENRICHMENT_RETRY = 3          # ретраи на одну карточку
ENRICHMENT_BATCH_TIMEOUT = 60 # таймаут на батч из 10 (если дольше — пометить как «надо повторить»)
```

В UI клиент видит прогресс: «Загружено деталей: 1240 / 5000 ... 24%».

### Что НЕ делать
- **Не запускать enrichment одновременно с циклом мониторинга** — мониторинг ходит в список (тяжёлый), enrichment — в карточки (легкие), но они делят общий лимит соединений у сервера. Лучше — серийно: сначала мониторинг (1 запрос), потом enrichment-батч.
- **Не идти выше 10 параллельных** без замеров — может схватить rate-limit. 10 = безопасный потолок, проверенный.
- **Не enrich'ить при каждом цикле мониторинга** — только новые id, которых нет в БД с заполненной деталью.

## Что становится возможным

Помимо очевидного «фильтры быстро»:

- **«Покажи лоты крупнее 50 га рядом с Владивостоком»** — комбинированный фильтр + bbox карты, 50 мс ответ
- **«Покажи лоты, где меняется статус»** — историческая таблица (добавим `lot_changes` для логирования)
- **«Сравни 3 лота»** — выбрать 3 чекбоксами, вывести таблицу сравнения
- **«Экспортировать в Excel то, что вижу»** — кнопка «Скачать .xlsx» с текущим фильтром
- **«Поделиться лотом по ссылке»** — `localhost:8080/catalog/lot/9990` копируется и работает у того, кто открывает в браузере свой `localhost`
- **Тёмная тема, мобильный режим** — стандартно для современного веб-UI

## Влияние на оценку

Это **расширение MVP**, не замена. Добавляет к 7-9 дням базового MVP:
- Enrichment-worker для детальных карточек: **+1 день**
- Каталог-таблица с фильтрами и поиском: **+2 дня**
- Карта Leaflet с кластеризацией: **+1.5 дня**
- Доп. эндпоинты, тесты, полировка: **+1 день**

Итого: **+5-6 дней, ~50-70к ₽**. Полная сумма MVP с каталогом — **200-250к ₽ за 12-15 дней**.

Окупается одной вещью: клиент сэкономит сотни часов работы со штатным сайтом. У него и его команды появится **рабочий инструмент**, а не просто уведомлятор.
