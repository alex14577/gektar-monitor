# Производительность сервера: критическое открытие

## Измерения (12.05.2026)

| Запрос | Время | HTTP | Получено | Возвращено строк |
|---|---:|---|---:|---:|
| `?region=1&per-page=20` (первый) | **81 с** | 200 | 268 KB | 20 |
| `?region=1&per-page=50` | **151 с** | 200 | 368 KB | **50** |
| `?region=1&per-page=100` | **134 с** | 200 | 368 KB | **50** (cap) |
| `?region=1&per-page=200` | **128 с** | 200 | 368 KB | **50** (cap) |
| `?region=1&per-page=500` (90с timeout) | >90 с | timeout | данные есть | 50 |
| Повторный `?region=1&per-page=20` | >60 с | timeout | — | — |

## Выводы

### 1. Сервер катастрофически медленный
Генерация одной страницы занимает **80–150 секунд**. Это не сеть (передача 268 КБ — секунды), это **серверный рендеринг**: Yii2 PHP идёт в БД, считает фильтры, делает JOIN'ы по большой таблице лотов, рендерит HTML. Видимо, у них тяжёлые SQL-запросы и нет нормального кеша.

### 2. `per-page` режется на **50**
Сервер принимает любое значение `per-page=N`, но **возвращает максимум 50 строк**. Это серверная защита, обойти нельзя.

### 3. Под нагрузкой сервер начинает таймаутить
После нескольких подряд тяжёлых запросов сервер перестал отвечать в течение 60 секунд. Возможные причины:
- Rate-limit (хотя при разведке без авторизации мы его не видели)
- Сервер закешировал «плохое» состояние под нашу сессию
- Простой пере-загрузки одного бэкенда; следующий запрос приходит на тот же узел

### 4. PJAX тест не успел отработать
Гипотеза «PJAX-запрос вернёт меньше HTML и быстрее» не проверена — сервер уже тормозил к моменту теста.

## Последствия для архитектуры

### Один цикл мониторинга при `per-page=10` (финальное решение, см. [[decisions-log]])
- При sort + early exit типичный цикл = **1 страница** вместо ~6 при фул-скане.
- Время одной страницы при `per-page=10` ниже, чем при 50 (меньше работы серверу), но порядок такой же: десятки секунд под нагрузкой, секунды в норме.
- Метрики времени ответа (от размера страницы зависят слабо): сетевая передача — секунды; основное время — рендеринг PHP/Yii2.
- В норме (5-30 с/запрос): цикл ~5-30 с при 1 странице → интервал 5-15 минут безопасен.
- Под техработами (60+ с/запрос для `per-page=10`): цикл ~1 минута при 1 странице → интервал 15-30 минут.
- При интервале 15 минут пользователь узнаёт о новом лоте в среднем через ~7 минут после появления.

### Если медленный сервер — это норма (а похоже на то)
- **Параллельные запросы страниц** не помогут (одинаково тяжёлые, нагрузим сервер ещё сильнее и схватим бан).
- Распараллеливать **по регионам** — теоретически безопаснее (другие маршруты в БД), но политически плохо: 2-4× нагрузка на гос-сервер.
- **Решение**: последовательно, с паузой 2-5 сек между запросами, интервал между циклами **30-60 минут**.

### Если медленность из-за моего IP / геолокации
- Я тестирую с серверного IP вне РФ.
- У пользователя на ПК в РФ может быть **существенно быстрее** (соседняя сеть, CDN, географическая близость).
- **Это надо проверить с ПК пользователя** перед финализацией интервала мониторинга.

## Что делать дальше

1. **Перепроверить таймингы с ПК пользователя** (РФ-сеть) — может оказаться, что страница рендерится за 5-10 секунд, и проблема в моей геолокации.
2. **Заложить в архитектуру**:
   - Конфигурируемый интервал между запросами и между циклами.
   - Идемпотентность цикла (можно прервать в любой момент).
   - Расчёт «эффективный интервал» по последним 10 циклам: если цикл занял 18 мин, следующий запуск через 30, если 5 мин — через 15.
3. **Уведомление пользователю**: «лоты появляются через ~30 минут после появления на сайте» — это реалистично, не врать про «мгновенно».

## Цитата из risks-legal

> Не дудосить гос-сервер. 1 запрос раз в 2-5 секунд при цикле каждые 30+ минут — социально приемлемо.
