# Server-performance v3 — authenticated session

## TL;DR

1. **Сессия рабочая**: cookies оператора ЕСИА действительны, все cabinet-endpoints вернули 200. Сессия не протухла за весь цикл исследования (~15 мин активных запросов).
2. **PJAX ПОДТВЕРЖДЁН**: сервер возвращает фрагмент 88 KB вместо 269 KB (3× меньше), `data-key` селекторы работают — парсер совместим напрямую. Время рендеринга одинаковое (~71 с) — узкое место в БД, не в генерации HTML.
3. **Export 403**: `POST /cabinet/start-export-freelot` отвергает запрос с CSRF из cookie (Forbidden). Без валидного server-side CSRF-токена export недоступен.
4. **Sort `-DATE_CREATE` работает** и показывает новейшие лоты первыми (ID 9994/9995, 14.05.2026). Early-exit стратегия практически применима.
5. **Скорость рендеринга**: 47–131 с/страница, без улучшений vs baseline 12.05.2026 (81–151 с). Проблема — серверная (PHP/Yii2 + DB), не сетевая.

---

## Verification of v2 hypotheses

### H1. PJAX — фрагментный ответ (TOP priority)

**Статус: CONFIRMED (частично)**

| Параметр | Значение |
|---|---|
| Полная страница | 269,327 bytes |
| PJAX фрагмент (`X-PJAX: true` + `X-PJAX-Container: #free-lots-pjax-container`) | 87,807 bytes |
| Экономия | **3.07× меньше** (181 KB saved) |
| Гzip (est.) | полная ~27 KB → PJAX ~9 KB |
| Фрагмент? | **Да** — начинается с `<div class="content-in__body">`, без `<html>` |
| `data-key` rows в PJAX | **20 строк** — идентично полной странице |
| Время рендеринга | **71.39 с** — столько же, сколько полная страница (71.40 с) |

**Вывод**: PJAX экономит трафик (3×), но НЕ ускоряет server rendering. Узкое место — SQL-запрос к БД, а не генерация HTML. Парсер (`tr[data-key]`) работает на PJAX-ответе без изменений.

**Рекомендация**: добавить `X-PJAX` заголовки к list-запросам — бесплатная экономия bandwidth. При мониторинге с gzip PJAX даёт ~9 KB vs ~27 KB (экономия ~18 KB / запрос).

### H2. Export endpoint — CSV/XLSX выгрузка

**Статус: DENIED (403)**

`POST /cabinet/start-export-freelot` вернул **403 Forbidden** несмотря на наличие:
- валидного `PHPSESSID` и `session-cookie` (session active)
- `_csrf` из cookie (десериализованный Yii2 cookie hash: `WzL0BIlnEgE-9LMIfNCIt2eYOSz9rKXq`)
- `X-Requested-With: XMLHttpRequest`

**Причина**: Yii2 CSRF protection для `POST` требует токен из `<meta name="csrf-token">` HTML-страницы (server-side ephemeral token), а не из cookie. Cookie `_csrf` — это signed verifier, не сам токен.

`GET /export-file/check-export` без ID вернул `{"finished":true,"files":[]}` (200 OK) — endpoint доступен, но пустой (нет активных задач).

**Рекомендация**: для доступа к export необходимо:
1. Загрузить страницу `/cabinet/free-lot` и извлечь `<meta name="csrf-token" content="...">` из HTML
2. Использовать этот токен в POST запросе

HTML-мета CSRF-тег в полученных страницах не найден (искали в `verify_session_list.html`). Возможно, сервер использует другой механизм или CSRF-токен появляется только в браузерном контексте.

**Альтернатива**: export через Playwright с реальным браузером — надёжнее, но сложнее архитектурно.

### H3. Sort `-DATE_CREATE` для early-exit

**Статус: CONFIRMED**

| Сортировка | Первые 3 лота (ID) | Дата |
|---|---|---|
| Default (без sort) | 1492, 1526, 1991 | 15.12.2021 — старейшие лоты |
| `sort=-DATE_CREATE` | 9994, 9995, 9990 | 14.05.2026 — сегодняшние лоты |
| `sort=-DATE_UPDATE` | 9995, 9994, 9990 | 14.05.2026 — недавно изменённые |

Сортировка `sort=-DATE_CREATE` работает корректно и показывает новые лоты первыми. **Early-exit применим**: при сохранении `max_known_id` достаточно запросить страницу 1 — если все ID ≤ max_known → новых нет → стоп.

## New findings

1. **`per-page=10` значительно быстрее**: 48 с vs 71 с (default per-page=20) и 131 с (per-page=50). Зависимость времени от числа строк подтверждена. Для early-exit мониторинга оптимальный баланс — `per-page=10` или `per-page=20`.

2. **Сервер хранит filter state per-session** (Yii2 GridView session storage). `data-filter-url` в ответе отражает сохранённые оператором настройки: `sort=-DATE_UPDATE&per-page=10`. При следующих запросах без явных параметров сервер может применять эти настройки.

3. **Всего лотов в регионе 1: ~2500** (все статусы). С `freeLotStatus=Свободен`: ~1000 лотов (50 страниц × 20). Operator filter_pocket: ~420 лотов (21 страница × 20). Предыдущая оценка v2 «~1050 лотов» пересмотрена.

4. **`freeLotStatus=Свободен` НЕ уменьшает объём страницы** (271 KB vs 269 KB для default). Фильтрация работает серверно, но рендеринг одинаково тяжёлый. При этом фильтр показывает 1000 лотов vs 420 в filter_pocket — то есть filter_pocket сужает набор.

5. **Только статус "Свободен" присутствует на текущих страницах** (все 50 лотов из per-page=50 имеют статус "Свободен"). Лоты с другими статусами ("Резерват", "Передан" и т.д.) на первых страницах не встречаются — они либо на последних страницах либо вообще не возвращаются в текущем фильтре.

6. **Сессия не ротируется**: `Set-Cookie` в response headers не содержит новых cookies. Сессия стабильна в течение ~15 мин исследования. Max-Age=86400 подтверждён (24 ч).

7. **Detail страница быстрая**: 5.35 с — если нужны детали конкретного лота, это не bottleneck. Лот ID 1492 (кадастровый номер 14:29:040004:523, статус Свободен, дата 15.12.2021).

8. **PJAX фрагмент содержит полную функциональность**: таблица, пагинация, ссылки на сортировку — всё присутствует в 88 KB фрагменте.

## Архитектурные импликации

### 1. PJAX — добавить к HttpClient (высокий приоритет)

Добавить заголовки `X-PJAX: true` и `X-PJAX-Container: #free-lots-pjax-container` ко всем list-запросам. Это снижает трафик в 3× без изменений в парсере. При gzip: 27 KB → 9 KB. Парсер (`BeautifulSoup`, селектор `tr[data-key]`) работает на фрагменте без модификаций.

```python
# В HttpClient.get_lot_list():
headers = {
    "X-PJAX": "true",
    "X-PJAX-Container": "#free-lots-pjax-container",
    "X-Requested-With": "XMLHttpRequest",
    "Accept": "text/html, */*; q=0.01",
}
```

### 2. Early-exit с `sort=-DATE_CREATE` (высокий приоритет)

Подтверждено работающим. Стратегия:
```
GET /cabinet/free-lot?FreeLotSearch[rfSubjectId][]=1&sort=-DATE_CREATE&per-page=20
→ проверить IDs: если max(ids) <= last_known_max_id → новых нет → стоп
→ иначе: обработать новые, сохранить новый max_id
```

### 3. Оптимальный per-page для мониторинга: 20

- `per-page=10`: 48 с, 10 строк. При 20 новых лотах за цикл — 2 запроса.
- `per-page=20`: 71 с, 20 строк. При 20 новых — 1 запрос.
- `per-page=50`: 131 с, 50 строк. Избыточно для early-exit.
- **Вывод**: `per-page=20` оптимально для early-exit (1 запрос типично, 71 с).

### 4. Export через browser CSRF — исследовать отдельно (средний приоритет)

CSRF из cookie не работает для POST. Для export нужен Playwright-сессия или предварительный GET страницы для извлечения CSRF мета-тега. Архитектурно: export = отдельный use-case, не заменяет мониторинг.

### 5. `freeLotStatus` filter — не использовать для уменьшения нагрузки

Фильтр по статусу не ускоряет рендеринг. Но фильтр `freeLotStatus=Свободен` увеличивает охват с 420 до 1000 лотов (filter_pocket ограничен). При инициализации базы полезен для seed.

### 6. Detail page — дешёвый endpoint (5 с)

Можно дозапрашивать детали конкретного лота (площадь, кадастровый номер) без значительного overhead.

### 7. Интервал мониторинга — подтвердить 15–30 мин

Типичный цикл с early-exit: 1 запрос × ~71 с = 1.2 мин + pause 5 с = 1.3 мин цикл. Интервал 15 мин означает среднее время обнаружения нового лота ~7.5 мин. Приемлемо.

## Этика / ограничения

- **Budget**: 11 запросов из 30
- **Cookies**: session cookie оператора (не опубликовано; в отчёте как `PHPSESSID=<redacted>`)
- **503/blacklist**: не получили — сервер стабильно отвечал на все 11 запросов
- **Session expired**: нет — сессия работала полный цикл (~900 сек суммарного времени), финальный HEAD вернул 200
- **Интервал**: 5 с между запросами, 11 запросов × (avg 70 с + 5 с) ≈ ~825 сек итого
- **Геолокация**: IP вне РФ. Возможен +10–30% latency vs пользовательский ПК в РФ
- **Export 403**: не обошли — уважаем ограничение, не перебираем токены
